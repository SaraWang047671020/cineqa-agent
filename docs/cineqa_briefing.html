核心概念

為什麼不是「看起來對就好」

生成式影片最常見的失敗不是畫質差，而是看起來很漂亮但根本不是你要的東西： 你要角色從畫面左邊走到右邊，結果是鏡頭在跟拍、角色其實原地沒動； 你要門被踢破，結果門破了之後又自己癒合。這些破綻用肉眼看很容易放過。

CineQA 的做法是把「這支影片對不對」這個模糊問題，拆成 6–12 條各自獨立、可以打勾或打叉的具體主張（claim）， 逐條驗證後產出一份 Verification Ledger。每條 claim 有三種判定：

MATCH 影片符合這條主張
MISMATCH 影片牴觸這條主張
CANNOT_DETERMINE 證據不足，系統承認判不了

第三種判定很重要：它是系統誠實承認「這一條我沒把握」的出口， 而不是硬在對錯之間丟銅板。整套統計決策層（後面會講）就是為了決定什麼時候該說這句話。

完整流程

這是一條有序的 pipeline，編號代表實際執行順序

  1. 01

    Claim 抽取

    把導演 prompt（可能好幾百字）蒸餾成 6–12 條高影響力的可驗證主張，每條標上型別、時間屬性、抽樣策略與所屬 tier。UI 另外在最前面注入一條 Tier 0 的通用物理檢查。

    engine/claims.pyextract_claims()temperature 0.1
  2. 02

    Pre-Flight 關鍵幀

    在燒掉影片額度之前，先生一張「首幀」做低成本 QA；需要時再用 image-to-image 從首幀衍生一張「尾幀」，讓兩張圖的角色與美術風格保持一致。首尾幀之後會餵給 Veo 做插值，用畫面鎖住動作的起點與終點。

    engine/storyboard.pygenerate_storyboard()base_image_path = I2I
  3. 03

    影片生成

    呼叫 Veo，可帶入首幀、尾幀（frame interpolation）、最多數張參考圖（ASSET / STYLE）、負向 prompt、固定 seed 與 inpaint mask。seed 會記錄在 take 上，讓後續重生成可以只變動 prompt、控制變因。

    engine/generator.pyveo-3.1-fast-generate-0011080p
  4. 04

    抽幀

    依 claim 的時間屬性與型別決定抽樣密度：靜態類抽 3 幀；顏色／數量／風格類上限 5 幀；動作與方向類最多 20 幀。多執行緒平行呼叫 ffmpeg，縮到寬 800px 以控制上傳量。

    engine/verify.pyextract_frames()ThreadPoolExecutor(8)
  5. 05

    逐條驗證

    每條 claim 獨立組一份 prompt（依型別插入不同的檢查區塊），連同抽出的幀送進 Gemini，要求以結構化 JSON 回覆。同一條 claim 平行跑 3 票。claim 與 claim 之間也是平行處理。

    engine/pipeline.pystream_pipeline()ThreadPoolExecutor(5)
  6. 06

    統計決策

    3 票丟進 Split-Conformal 判決層，算出 prediction set。集合大小為 1 才算「可自主判定」；大於 1 代表模型內部有分歧，走多數決或直接標記為不確定。

    agents/conformal_judge.pyLAC scoreconfidence 0.80
  7. 07

    修正與重生（Auto-Heal）

    把失敗的 claim 交給 remediator，它會先透過 MCP 去 ClickHouse 查「同類問題以前怎麼修好的」，再產出新的正向／負向 prompt 與 token 級修改清單，重新生成一支 take，然後回到步驟 04 再驗一次。

    agents/remediator.pyGemini function callingMCP tool
寫入時機：每一輪驗證跑完，ledger 會在背景執行緒非同步寫進 ClickHouse，不阻塞畫面； 第二個 take 之後還會額外寫入一筆「修正案例」——這就是下一輪 Auto-Heal 能查到的記憶。

Claim 分類

型別決定驗證時套用哪些檢查規則

型別（type）

型別檢查什麼驗證時額外套用
action動詞是否真的發生（不只是「物件存在」）隱含主體推導、接觸與後果檢查
direction螢幕座標上的實際位移鏡頭跟拍 vs 主體位移的拆解
relative_positionA 與 B 的相對位置，且需跨幀維持質心座標數學檢查
relative_size尺寸比較，需對應到正確的幾何軸深度平面與透視校正
color顏色與屬性綁定是否正確—
count數量只計顯著實例，忽略背景雜訊
state狀態與狀態轉換時序比對
style美術媒材與風格渲染技法判別
physics_sanityTier 0：全域物理與拓樸連續性物體恆存、肢體連續、穿模、姿態跳動

層級（tier）

Tier意義
tier1_causal_action核心因果時間軸：觸發事件、物理反應、動作完成
tier2_spatial_geometry嚴格的空間對位與構圖邊界
tier3_multimodal_consistency與概念圖／分鏡的一致性，以及整體美術風格
tier4_physics_defect_control物理定律與負向缺陷抑制
設計上的關鍵決定：Tier 0 的物理檢查只由那一條專屬 claim 負責。 其他 claim 不再重複掃描整支影片的物理問題——否則影片任何角落的一個小瑕疵，會把所有不相關的 claim 一起拖下水判死。

單條 claim 怎麼被判

組 prompt → 附帶客觀證據 → 結構化回覆

五步驗證協定

每條 claim 的 prompt 都以同一套協定開頭：拆解子事實 → 客觀觀察與座標錨定（不得提前下結論）→ 證據充分性評估 → 區分 AI 生成瑕疵是否落在判斷範圍內 → 形成判定並做反向因果檢查。

依型別掛載的檢查區塊

區塊掛載條件作用
BLOCK_SPATIAL一律把比較詞對應到正確幾何軸，避免用面積冒充高度
BLOCK_ACTIONtype = action區分「動作發生」與「狀態存在」；要求觀察實際接觸與後果
BLOCK_DIRECTIONtype = direction要求算出螢幕座標，並拆解鏡頭跟拍造成的假位移
BLOCK_POSITIONINGclaim 含方位詞質心座標的數學比較，且需跨幀維持
BLOCK_SEQUENTIALtemporal = sequential連續鏡頭判斷、流體動力學、因果完整性、拓樸持久性
BLOCK_PHYSICS_LAWStemporal = sequential重力支撐、動量守恆、剛體碰撞、材質對應運動
BLOCK_PHYSICS_SANITYtype = physics_sanity物體恆存、肢體連續、穿模、姿態跳動
BLOCK_COUNT / STYLE / REFERENCE對應型別／有參考圖數量、美術風格、與概念圖的一致性

給模型不會幻覺的客觀證據

VLM 不擅長用眼睛估計「兩幀之間到底動了多少」，但傳統 CV 演算法很擅長。 所以每張幀的標籤除了時間戳，還會附上與前一幀的灰階像素差值，並標記等級： 

[FRAME_3 @ t=1.20s]
[FRAME_4 @ t=1.40s | pixel-diff vs prev frame: 2.1 (LOW，可能停滯)]
[FRAME_5 @ t=1.60s | pixel-diff vs prev frame: 48.3 (HIGH，可能跳接)]

判斷「有沒有跳接」時，模型被要求以這個數字為主要依據，而不是憑視覺印象—— 因為構圖差很多不代表是剪接，那通常只是抽樣間隔造成的。

結構化回覆

模型必須以固定 schema 回覆，重點欄位：

欄位內容
checkable_components這條 claim 被拆成哪些子事實
frame_observations逐幀客觀描述（不含結論）
motion_anchoring_check主體首尾幀的 X 座標百分比，以及背景是否位移
spatial_geometry_check各實體佔畫面高／寬的百分比與數學驗算
physics_law_grounding_check四條物理定律哪些適用、是否成立，須引用幀號
physics_and_reality_sanity_check本 claim 主體是否遭遇幻覺類瑕疵
evidence_sufficiency_check支持／牴觸證據分別在哪幾幀，充分性等級
verdict / confidence最終判定與自評信心

共識與統計決策

3 票 → prediction set → 判定

同一條 claim 平行跑 3 次（第一票 temperature 0.1，其餘 0.3），得到一組投票分佈。 這組分佈不是直接多數決，而是先進入 Split-Conformal（LAC） 判決層。

校準怎麼做

  1. 對每筆標註資料算 non-conformity score：s = 1 − P(真實類別)
  2. 取這些分數的 ⌈(n+1)×0.80⌉ / n 分位數，得到門檻 q̂（目前為 0.667，n = 92）
  3. 判定時：1 − P(類別) ≤ q̂ 的類別，全部放進 prediction set
投票Prediction set最終判定
MATCH ×3{MATCH}MATCH 可自主判定
MATCH ×2, MISMATCH ×1{MATCH, MISMATCH}MATCH 多數決，標記為不確定
MATCH ×1, MISMATCH ×2{MATCH, MISMATCH}MISMATCH 多數決，標記為不確定
三票分歧{全部}CANNOT_DETERMINE

每一列 ledger 都會記下 conformal_set_size 與 is_autonomous，並寫進 ClickHouse。 所以「系統有多少比例的判斷是自己就能拍板的、多少比例需要人工複核」， 可以直接用一句 SQL 查出來——這是整套風險控制機制存在的意義。

要注意的限制：92 筆校準樣本在 80% 信心水準下，實測覆蓋率平均 0.848、 標準差約 0.11。也就是說這個保證本身還有不小的變異，樣本數需要再擴充才能講得更硬。

ClickHouse 串接

兩條獨立的路：寫入是普通 client，讀取走 MCP

ClickHouse 在這個專案裡不只是「事後分析用的資料庫」，而是修正 agent 的長期記憶。 寫入與讀取走的是兩條完全不同的路徑，而且只有讀取那條需要經過 MCP。

連線層

database/clickhouse_init.py 的 get_client() 是模組級單例， 連線只建立一次並重複使用，避免每次寫入都重跑一次 TLS 握手。連線帶 5 秒建立逾時與 10 秒讀寫逾時—— 沒有逾時的話，只要網路有任何問題，UI 就會無聲地卡住很久。

兩張表

表一列代表關鍵欄位
verification_ledger 某個 take 的某一條 claim 的驗證結果 scene_id, take_num, claim_id, claim_type, verdict, confidence, conformal_set_size, is_autonomous, consensus_votes, observed
remediation_history 一次「修正嘗試」的完整案例 claim_type, claim_text, failure_observed, refined_positive_prompt, negative_prompt, take_num_before, take_num_after, outcome_verdict

記憶迴圈

remediation_history 只在第二個 take 之後才寫，而且只寫前一輪判 MISMATCH 的那些 claim。 每一列記錄的是一個完整故事：

  • failure_observed：前一輪那條 claim 的實際失敗描述
  • refined_positive_prompt：針對它做的具體措辭修改（來自 remediation plan 的 token surgery）
  • outcome_verdict：這一輪重驗的結果——也就是「這個修法有沒有用」的標籤

讀取：MCP tool

mcp_server.py 以 MCPServer 起一個 stdio server，對外只暴露一個工具： 

search_remediation_history(claim_type: str) -> str

SELECT claim_text, failure_observed, refined_positive_prompt
FROM remediation_history
WHERE claim_type = %(ct)s AND outcome_verdict = 'MATCH'
ORDER BY ts DESC LIMIT 3

注意 outcome_verdict = 'MATCH' 這個條件：只回傳真的修好的案例， 失敗的修法不會污染記憶。remediator 把這個函式當成 Gemini 的 tool 掛進 chat session， 由模型自己決定要不要查、查哪個 claim_type——這是「agentic」的部分，不是我們寫死的流程。

記憶要先累積才有效。查詢條件是「修成功的案例」，所以必須先跑過幾輪完整的 Auto-Heal（失敗 → 修正 → 重生 → 通過），表裡才會有東西。Demo 前需要預先批次跑資料。

現況與待辦

給組員的誠實版本

  • 可用
    驗證主流程

    claim 抽取 → 抽幀 → 3 票共識 → conformal 判決 → ledger，端到端可跑。實測一支有真實瑕疵的影片為 5/8 通過，失敗的三條理由具體且可對照。

  • 可用
    ClickHouse 寫入與 MCP 讀取

    連線單例、逾時、批次寫入、MCP server（已修正為 mcp 2.x 的 MCPServer API）皆已打通。

  • 待驗證
    整體精確率

    目前只有單一案例的觀察，尚未用 eval/run_precision_eval.py 跑過標註集量出精確率。校準資料的產出時間也早於近期多輪 prompt 修改，建議重新校準。

  • 已知問題
    Claim 抽取會自行加入細節

    觀察到抽取階段會憑空補上原始 prompt 沒提到的具體零件（門鎖、門栓、拱形走廊），導致產生無法通過的假 claim。需要在抽取 prompt 加上「不得引入原文未指定的具體名詞」的硬規則。

  • 已知問題
    否定式 claim 的空洞通過

    「停住時沒有穿透牆壁」這類以「沒有發生 X」為條件的 claim，當前提根本沒發生時會被判 MATCH，但這個通過是空的。需要要求先確認前提成立，否則回 CANNOT_DETERMINE。

  • 已知問題
    UI 畫面重整

    Streamlit 畫面偶發持續重整、右上角執行指示不停。尚未定位，需要確認閒置時是否自發、WebSocket 是否反覆重連。

  • 待確認
    官方 mcp-clickhouse 合規

    比賽規則寫的是透過「官方 mcp-clickhouse」存取，我們目前是自建 MCP server 包 ClickHouse。精神一致，但字面上是否算數需要跟主辦確認。

  • 未完成
    缺陷定位與局部重繪

    兩段式 bbox 定位（先問哪一幀、再單獨問座標）與 mask 局部重繪的骨架已存在，但尚未接成完整可用的流程。

踩過的坑，請記得：Streamlit 只會重跑主腳本，不會重新載入已 import 的模組。 改了 engine/verify.py 之後如果沒有完整重啟 process，UI 跑的還是舊版程式碼—— 我們為此追了好幾輪不存在的 bug。ui/app.py 頂端已加入對應的 reload 清單， 但改動核心模組後仍建議完整重啟。

怎麼跑起來

本機開發環境

# 1. 依賴
pip install -r requirements.txt

# 2. 環境變數（.env）
GOOGLE_CLOUD_PROJECT=...
GOOGLE_CLOUD_LOCATION=us-central1
DEFAULT_GEMINI_MODEL=gemini-2.5-flash
CLICKHOUSE_HOST=...
CLICKHOUSE_USER=default
CLICKHOUSE_PASSWORD=...

# 3. 建立 ClickHouse 資料表（只需一次）
python database/clickhouse_init.py

# 4. 確認 MCP 記憶鏈路通了
python -c "from agents.mcp_client_wrapper import search_clickhouse_memory; print(search_clickhouse_memory('action'))"
#   預期：No historical fixes found for claim type: action.（表示通了，只是還沒資料）

# 5. 起主程式
streamlit run ui/app.py

另外有兩支獨立工具：eval/run_precision_eval.py 用標註集量測驗證精確率， eval/calibrate_mapie_formal.py 重新產生 conformal 判決層的校準資料。
