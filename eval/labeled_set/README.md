# 標註集建置指南

對應 `pain-point-analysis/ai-影片生成重跑浪費/analysis.md` 第 8 節「實驗 1」：驗證引擎精確率測試，判準 ≥85%（誤報率 ≤15%）。

## 這份標註集要解決什麼問題

系統會自動抽取 claim、跑驗證、給出 verdict。但我們要知道**系統判斷得準不準**，就需要一組「人已經看過影片、知道正確答案」的資料去對照——這就是這份標註集的作用。**沒有這一步，後面所有的精確率數字都是自吹自擂。**

## 選片策略（20-30 顆鏡頭）

不要隨便選，要覆蓋這幾個維度，否則精確率數字會有偏差：

| 維度 | 建議涵蓋 |
|---|---|
| Claim 類型 | 七類（count/direction/relative_position/relative_size/color/state/action）至少各 2-3 顆 |
| 時序類型 | static 主張與 temporal 主張都要有，建議各半 |
| 已知答案 | 故意混入**明顯正確**、**明顯錯誤**、**邊界模糊**三種情況，不要全部是好例子（否則測不出誤報率） |
| 來源 | 建議一半用團隊自己的 Veo 生成素材，一半用 Hell Grind 公開素材裡已知失敗案例（門不會破、角色瞬移、巨人縮水）當「已知錯誤」的正樣本 |

## 標註流程

1. 把腳本裡的一段場次描述放進 `source_text`
2. 讓系統（或人工）抽出 claim，填進 `claim_text` / `type` / `verifiable` / `temporal`
3. **人親自看過對應的影片片段**，在 `ground_truth_verdict` 填入正確答案：`MATCH` / `MISMATCH` / `CANNOT_DETERMINE`
4. 如果人自己都看不出來（畫面模糊、遮擋、判斷有爭議），直接標 `CANNOT_DETERMINE`，不要勉強猜——這樣才能測出系統的棄權邏輯準不準
5. **`relative_position`／`color`／`state` 這類名義上「靜態」的主張，遇到會動的主體時，用整支影片的主導行為判斷，不是只看第一幀的構圖**（2026-08-21 補充）：例如「狗在腳踏車右側」這種空間關係主張，如果狗中途跑動換邊，左右關係在影片裡並沒有穩定成立，即使每一格畫面本身都清楚可辨（不是證據不足的情況），也要標 `MISMATCH`，不是 `CANNOT_DETERMINE`——`CANNOT_DETERMINE` 保留給「看不清楚」，不是「看得清楚但這件事中途變了」。跟 `c_0013`（雨衣女子跑下樓梯，prompt 說下樓但實際往上爬）是同一個判斷邏輯：依整支影片的實際主導行為判定，不是只看開頭那一刻。
   - **「主導行為」要看佔比/是否為最終狀態，不是有任何一點反向動作就算矛盾**：例如滑板先短暫往上（像 drop-in 上坡的自然鋪陳）、接著整段時間都在下滑，最終狀態明確是「下降」，這種情況判 `MATCH`，跟前面「狗換邊之後沒換回來、最終沒有穩定成立」的情況不一樣——差別在於反向的那段是**短暫、不影響整體結論**，還是**持續到影片結束、直接推翻了 claim 作為整體描述的成立**。
